1. Purpose and delivery principles
This document converts the client's Phase 2 feedback into an actionable
implementation and verification plan. The objective is to make the
existing platform reliable, consistent and practical for daily business
use.
Primary delivery goals
1. Resolve the core workflow and data-transfer issues before adding new
   functionality.
2. Ensure information entered once remains accurate throughout the
   complete workflow.
3. Make the interface clean, consistent and fully Dutch for end users.
4. Give administrators, partners and customers the correct information
   and permissions for their roles.
5. Complete internal testing before presenting changes for client
   review.
6. Provide one consolidated progress update per week.
Scope control
- Treat the ten sections in this document as the Phase 2 feedback
  scope.
- Do not introduce unrelated features while the reported core issues
  remain unresolved.
- Preserve existing working functionality unless a change is required
  by these requirements.
- Confirm any requirement that changes the agreed scope, timeline or
  third-party costs with the client before implementation.
- Do not describe an item as complete until its acceptance criteria
  have passed.

3. Detailed functional requirements
3.1 Dashboard and general interface
Client-reported issues
- Mock-up sections are still visible.
- The interface contains areas that are not part of the practical
  workflow.
- The platform is not fully translated into Dutch.
Required implementation
1. Audit all dashboards and navigation menus for demo, mock-up,
   placeholder and non-functional sections.
2. Hide or remove mock-up sections from production-facing roles. Retain
   internal development material only where required and inaccessible
   to normal users.
3. Keep the interface focused on currently agreed business workflows.
4. Translate every user-facing element into Dutch, including:
   - Navigation labels and page titles.
   - Buttons, links, tabs and menus.
   - Form labels, placeholders and helper text.
   - Validation messages and error messages.
   - Status names, filters and table headings.
   - Empty states, confirmation dialogs and notifications.
   - PDF/document labels where generated by the platform.
5. Use one consistent Dutch terminology list across Admin, Partner and
   Customer environments.
6. Check responsive layouts after removing or renaming sections.
Acceptance criteria
- No placeholder or mock-up sections are visible to normal production
  users.
- All user-facing labels and fields are Dutch.
- The same business concept uses the same Dutch term throughout the
  platform.
- No navigation item leads to an unfinished or irrelevant page.
- Existing authorised workflows remain accessible.
3.2 Leads and product configuration
Client-reported requirements
- Location and Desired dimensions must be free-text fields, not
  predefined selections.
- Custom product fields and options under Settings appear to work.
- The client must manage product categories, materials and
  configuration options through Settings.
- Existing names and configuration fields need a consistency review.
Required implementation
Lead form
1. Change Location to a free-text input.
2. Change Desired dimensions to a free-text input.
3. Preserve the exact value entered by the user, including units,
   separators and descriptive text.
4. Do not silently replace free-text values with predefined options or
   normalised values.
5. Apply appropriate length limits and safe input validation without
   restricting normal descriptions.
Settings / product configuration
Provide authorised administrators with the ability to create, edit,
activate/deactivate and manage:
- Product categories.
- Materials.
- Wood types.
- Product configuration fields.
- Configuration options and values.
Each configurable item should have, where relevant:
- A clear display name.
- A stable internal identifier.
- Active/inactive status.
- Optional description.
- Display order.
- Created/updated timestamps.
- Validation to prevent accidental duplicate names within the same
  configuration scope.
Existing data review
1. Audit existing category, material, wood type and field names.
2. Identify duplicates, spelling variations and inconsistent naming.
3. Propose a mapping before merging or renaming existing values.
4. Preserve historical records and references when a configuration item
   is renamed or deactivated.
5. Do not delete configuration values that are already referenced by
   leads, partner requests, quotations or projects.
Acceptance criteria
- Location and desired dimensions accept ordinary free text.
- An administrator can manage categories, materials, wood types and
  options without developer intervention.
- New configuration values appear in the relevant forms.
- Existing records remain readable after configuration changes.
- Duplicate or inconsistent configuration values are identified and
  resolved through an approved mapping.
3.3 Partner price requests and quotation editor --- critical workflow
Client-reported issues
The quotation editor has selected the wrong product type, displayed
incorrect dimensions and included specifications that were not
requested. Submitted partner price requests cannot be reopened and
inspected properly.
Required outcome
Information entered in a lead or partner price request must transfer
accurately into the quotation editor. The user must not need to re-enter
information already captured. The quotation editor should allow optional
extras to be added or adjusted without changing the original request.
Required data transfer
At minimum, transfer and preserve:
- Lead reference and customer reference.
- Product type.
- Product category.
- Location.
- Desired dimensions, exactly as entered.
- Materials.
- Wood types.
- Selected specifications and configuration options.
- Quantities, where applicable.
- Partner price and price breakdown, where applicable.
- Notes and relevant attachments.
- Request date, partner reference and request status.
Implementation requirements
1. Establish one canonical data structure for the product/request
   details used by the lead, partner price request and quotation
   editor.
2. Map each source field explicitly to its destination field. Do not
   rely on loosely matched labels or default product selections.
3. Use stable IDs for configured categories, materials, wood types and
   options. Retain the original display values for historical review.
4. Preserve free-text values such as dimensions and location exactly.
5. Do not add default specifications unless they were explicitly
   selected or are clearly identified as optional suggestions.
6. On quotation creation, prefill the editor from the selected
   lead/partner request.
7. Keep source-request data distinguishable from quotation-only
   changes.
8. Allow optional extras to be added, removed or adjusted in the
   quotation without overwriting the original request.
9. Show the source request reference in the quotation editor.
10. If required source data is missing or ambiguous, show a clear
    warning and require review rather than silently selecting an
    incorrect product or specification.
Reopen and inspect submitted partner price requests
1. Add a view/details action for submitted requests.
2. Allow authorised users to reopen a submitted request in read-only
   review mode.
3. Display the complete submitted snapshot, including dimensions,
   product type, materials, wood types, selected specifications, notes,
   attachments and partner pricing.
4. Show who submitted the request and when.
5. If editing/resubmission is supported, preserve the original
   submitted version and record the later revision separately.
6. Apply role-based access so users can only view requests they are
   authorised to access.
Data integrity and traceability
- Store a snapshot of the request at submission time.
- Link the quotation to the exact source request and lead.
- Record any quotation-specific changes separately.
- Avoid recalculating or replacing historical request details when
  Settings configuration changes later.
Acceptance criteria
- A test lead with known product type, dimensions, materials, wood
  type and specifications opens in the quotation editor with every
  value matching the source.
- No unrequested specification is added.
- No incorrect default product type or dimension is substituted.
- Partner pricing is transferred to the correct fields and is
  traceable to its source.
- Optional extras can be changed without altering the original
  request.
- A submitted partner request can be reopened and its complete
  contents inspected.
- Historical request details remain unchanged after later Settings
  edits.

3. Validate required fields and return actionable validation messages.
4. Ensure project creation is tenant/company scoped and linked to the

5. Prevent duplicate project creation caused by retries or repeated

6. Show a clear success state and open the created project.
Lead-to-project conversion

2. Transfer customer identity, product details, dimensions, materials,

4. Avoid creating a second customer record when the customer already
   exists.
5. Show a conversion summary or validation step when required data is

6. Record conversion time and initiating user.
Customer identity consistency
1. Use a single canonical customer record/reference.
2. Resolve customer names from that record rather than maintaining

3.5 PDF generation and documents
Client-reported issues

- Invoice PDFs need better spacing and readability.
Required implementation
Quotation PDF
1. Trace the PDF generation endpoint, authentication, file response

3. Ensure authorised users can download the correct quotation.
4. Use a clear error message if generation fails.

- Clear spacing between sections.
- Readable typography and consistent font sizes.

- Clear invoice number, date and payment details.

- Clearly separated tax/VAT and grand total.

- Consistent margins, headers and footers.
Acceptance criteria
- Quotation PDF downloads directly and does not redirect to the
  homepage.
- PDF content matches the saved quotation data.
- Invoice PDF is readable on screen and when printed.
- Long descriptions and multi-page invoices do not overlap or get
  clipped.
- Unauthorised users cannot download another customer's or company's

3.6 Customer portal, status synchronisation and notifications
Client-reported issues
- Admin changes are not always reflected in the customer portal.
- Project statuses must synchronise across admin, partner and customer
  environments.
- Partner status Ready for delivery must update the corresponding
  project status.
- Customer delivery-date actions must appear in the project activity
  log.
- Important events must trigger admin bell notifications.
- Internal chat is not working correctly.
- Remove Mobile views and Delivery and aftercare from the customer
  portal.
- Simplify customer navigation.
- Client asks how customer email notifications will work.
A. Portal data synchronisation
1. Define one canonical project status model and an explicit mapping
   for Admin, Partner and Customer views.
2. When an authorised admin changes project information, update the
   shared project record and make the change visible in the relevant
   portal.
3. When a partner changes a project to Ready for delivery, update the
   canonical project status and show the mapped status in admin and
   customer environments.
4. Prevent one portal from displaying stale or conflicting status
   values.
5. Enforce role and company access on every status update.
6. Record status changes with actor, timestamp, previous value and new
   value.
B. Customer actions and activity log
Record at least:
- Customer approves a proposed delivery date.
- Customer requests a different delivery date.
- Customer submits a message or relevant project response.
- Admin or partner uploads or publishes a relevant document.
- Project status changes.
- Quotation is uploaded/published or approval is requested.
Each activity entry should include:
- Event type.
- Project reference.
- Actor and role.
- Timestamp.
- Relevant details, such as the proposed or requested date.
- A link to the relevant project or document, subject to permissions.
C. Admin notification bell
1. Create notifications for important customer and partner actions.
2. Display unread count and notification list in the admin bell.
3. Include a useful event summary, project reference and timestamp.
4. Allow authorised admins to open the relevant project from a
   notification.
5. Support read/unread state.
6. Avoid duplicate notifications when an event is retried.
7. Ensure notifications are scoped to the correct company and
   recipients.
D. Customer email notifications --- proposed behaviour to confirm
The expected workflow should be:
1. An admin uploads/publishes a quotation or other customer-facing
   document, or requests customer approval.
2. The system records the event and creates an in-app notification for
   the customer.
3. The system queues an email to the customer's registered email
   address using an approved email provider.
4. The email contains a concise message, project reference and secure
   link to sign in and view the relevant item.
5. The customer signs in and performs the requested action in the
   portal.
6. The action is saved to the project activity log and creates an admin
   notification.
7. Email delivery status and failures are logged for support and
   troubleshooting.
Important: Email notifications require an email service/provider,
verified sender domain, credentials/API key, sender details and agreed
email templates. The client must confirm whether an email provider is
already available and provide access through a secure method. Do not
claim the email integration is active until credentials are configured
and end-to-end delivery tests pass.

Recommended initial email events:
- New quotation published.
- Approval requested.
- Delivery date proposed.
- Delivery date changed.
- Important project status update.
- New customer-facing document published.
Allow notification preferences and avoid sending duplicate emails for
repeated events. Do not include sensitive project information in email
subject lines or unsecured links.
E. Internal chat
1. Test message creation, delivery, conversation loading and history
   retrieval.
2. Verify correct project/conversation association.
3. Verify sender identity and role permissions.
4. Handle empty, loading, failed-send and retry states.
5. Ensure messages persist after refresh and are not duplicated.
6. Confirm unread indicators and notification behaviour if included in
   the agreed chat scope.

4. Recommended technical implementation approach
This section describes the recommended engineering approach. It is an
implementation guide, not a claim that these changes have already been
made.
4.1 Establish canonical records and relationships
Use stable database relationships and identifiers for:
- Customer.
- Lead.
- Product category and configuration.
- Partner price request.
- Quotation.
- Project.
- Documents/attachments.
- Project activity.
- Notifications.
- Chat conversations and messages.
Avoid relying on customer names or display labels as database
relationships. Use IDs for relationships and resolve display names from
the canonical record.
4.2 Use explicit field mapping and snapshots
- Create documented mapping functions for each workflow transition.
- Validate required fields before creating downstream records.
- Store source references and submission snapshots.
- Preserve original request values for historical audit.
- Keep quotation extras separate from original request specifications.
- Avoid overwriting historical records when Settings configuration
  changes.
4.3 Make workflow operations safe
- Use database transactions for multi-record operations such as lead
  conversion.
- Add idempotency or duplicate protection for create/convert actions.
- Return meaningful API validation and failure responses.
- Log server-side errors with correlation/request IDs.
- Do not expose sensitive internal errors to end users.
- Enforce company/tenant scoping and role permissions on every API.
4.4 Synchronise status through one source of truth
- Define canonical project status values.
- Define allowed transitions and which roles may perform them.
- Map canonical statuses to each portal's Dutch display label.
- Write status changes to the shared project record.
- Create activity and notification events from the same successful
  state change.
- Ensure retries do not create duplicate activity or notifications.
4.5 Use reliable document delivery
- Generate PDFs from saved, validated records.
- Return correct content type and attachment headers.
- Verify authentication and authorisation before download.
- Log generation failures.
- Test large and multi-page documents.
4.6 Build event-driven notifications
For each supported event:
1. Save the underlying business change.
2. Record an event/activity entry.
3. Create in-app notifications for the correct recipients.
4. Queue email notifications where configured.
5. Track delivery outcome and retry transient failures safely.
A notification failure must not undo a successfully saved project or
customer action.

10. Definition of Done
A requirement is complete only when all applicable conditions are met:
1. The agreed behaviour is implemented.
2. Backend validation, permissions and company/tenant scoping are
   verified.
3. Data is saved correctly and remains correct after refresh/reload.
4. Error and empty states are handled.
5. Relevant unit, integration or end-to-end tests pass.
6. Related workflows pass regression testing.
7. Dutch user-facing text is checked.
8. Evidence is recorded in the issue tracker or QA report.
9. No known critical or high-severity regression remains in the
   affected workflow.
10. The item is included in the weekly update with an accurate status.
11. Client verification is completed where the requirement needs client
    acceptance.

12. Final delivery principle
The immediate objective is not to add more features. It is to make the
agreed Phase 2 functionality dependable.

The highest priority is the accuracy and continuity of business data
from the first lead through partner pricing, quotation, project creation
and the customer portal. Every downstream screen and document must
reflect the correct source information, and every important user action
must be traceable.

Phase 2 should be presented for approval only after the critical
workflows have passed internal QA and the client has had a clear
opportunity to verify the completed requirements.
